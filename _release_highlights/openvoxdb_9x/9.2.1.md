Notable changes in this release:

- The facts terminus in `openvoxdb-termini` now rejects a fact upload whose certname differs from the one in the request URL ([#669](https://github.com/OpenVoxProject/openvoxdb/pull/669)), which fixes [GHSA-859m-7qpm-85p7](https://github.com/OpenVoxProject/openvoxdb/security/advisories/GHSA-859m-7qpm-85p7), rated 7.7 high.
  OpenVox Server authorizes `PUT /puppet/v3/facts/<certname>` against the URL only, so a host with any valid agent certificate could overwrite the facts that OpenVoxDB stores for another node, and with them the result of every query that reads those facts.
  A server is affected when its `routes.yaml` sets the facts terminus to `puppetdb`, as the steps in [Connecting Puppet Servers to OpenVoxDB](connect_puppet_server.html) do.
- The fix is in the `openvoxdb-termini` package, which is installed on OpenVox Server hosts. On every primary server and compiler, upgrade `openvoxdb-termini` to 9.2.1 and restart `puppetserver`.
  Upgrading only the `openvoxdb` package does not fix the issue.
- Saving facts that already contain a `trusted` key no longer fails with `detected duplicate key "trusted"` when version 3 of the json gem is installed on the server ([#597](https://github.com/OpenVoxProject/openvoxdb/pull/597)).
  The OpenVox packages do not ship json 3. It arrives when `puppetserver gem install` installs a gem that depends on it.
- The `puppetdb_query` function accepts an optional hash after the query that sets the OpenVoxDB URL and the TLS files for that query (`url`, `ssl_cert`, `ssl_key`, `ssl_ca`, `ssl_crl`), so a manifest can query an OpenVoxDB that uses another CA ([#659](https://github.com/OpenVoxProject/openvoxdb/pull/659)).
- The `openvoxdb` package now requires `openvox-agent` 9.4.0 or later ([#655](https://github.com/OpenVoxProject/openvoxdb/pull/655)).
